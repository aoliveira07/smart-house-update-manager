PROJETO: Smart House Update Manager
CARTÃO: SH-005
PLATAFORMA: Home Assistant OS
TIPO: Home Assistant App
OBJETIVO: substituir as automações manuais de atualização existentes por um
aplicativo instalável, configurável e de fácil manutenção, incluindo também
reinicialização preventiva diária do host.

============================================================
1. OBJETIVO GERAL
============================================================

Desenvolver um Home Assistant App chamado:

Smart House Update Manager

slug:
smart_house_update_manager

O aplicativo deverá centralizar:

- atualizações automáticas do Home Assistant;
- atualizações de Home Assistant Apps;
- atualizações de software/HACS quando possível via entidades update;
- gerenciamento de backup antes de atualizações;
- controle de reinicializações;
- reinicialização preventiva diária do host;
- acompanhamento de jobs do Supervisor;
- validação pós-atualização e pós-reboot;
- histórico das execuções;
- painel web via Ingress;
- notificações de sucesso/falha;
- recuperação de execução após reboot.

A instalação deverá ser simples através de um repositório de Home Assistant
Apps hospedado no GitHub.

============================================================
2. COMPORTAMENTO ATUAL A SUBSTITUIR
============================================================

Existem atualmente seis automações:

01 - Backup antes das atualizações
02 - Detectar atualização concluída
03 - Atualizar Home Assistant Supervisor
04 - Atualizar Home Assistant Core
05 - Atualizar Home Assistant OS
06 - Atualizar aplicativos HACS e firmwares

Essas automações serão substituídas pelo App após homologação.

NÃO remover ou alterar as automações atuais durante o desenvolvimento.

A migração somente ocorrerá depois do App passar pelos testes reais.

============================================================
3. JANELA DE MANUTENÇÃO
============================================================

Horário padrão:

04:00

Deve ser configurável pelo usuário.

A rotina de atualização inicia nesse horário.

O App deve impedir duas rotinas de manutenção simultâneas.

Deve existir um lock persistente de execução.

============================================================
4. REBOOT PREVENTIVO DIÁRIO
============================================================

REQUISITO OBRIGATÓRIO.

O computador que executa o Home Assistant OS deverá ser reiniciado TODOS OS
DIAS, independentemente de existir atualização.

Horário padrão:

05:30

Deve ser configurável.

Essa rotina é independente das atualizações.

Portanto:

- nenhuma atualização disponível → reboot diário ocorre;
- atualização do Core ocorreu → reboot diário ocorre;
- atualização de Apps/HACS ocorreu → reboot diário ocorre;
- atualização do OS ocorreu → o reboot diário será usado para aplicar o OS;
- falha em uma atualização → o reboot diário continua sendo planejado,
  desde que não exista operação crítica ainda em andamento.

Utilizar Supervisor API:

POST /host/reboot

Não utilizar force=true por padrão.

============================================================
5. PROTEÇÃO ANTES DO REBOOT
============================================================

Antes de executar o reboot diário, consultar:

GET /jobs/info

Não reiniciar enquanto existir um job crítico ativo, incluindo:

- backup;
- restore;
- Core update;
- OS update;
- App update;
- instalação;
- migração;
- qualquer job que possa sofrer corrupção com interrupção.

Se 05:30 chegar e houver job ativo:

- registrar "reboot adiado";
- aguardar 5 minutos;
- verificar novamente;
- repetir até ficar seguro.

Criar timeout configurável, inicialmente 120 minutos.

Ao exceder o timeout:

- NÃO usar reboot forçado automaticamente;
- registrar erro;
- criar notificação no Home Assistant;
- manter o App operacional;
- registrar que o reboot diário falhou.

============================================================
6. DESCOBERTA DE ATUALIZAÇÕES
============================================================

Usar prioritariamente as APIs oficiais do Supervisor.

Consultar:

GET /available_updates
GET /core/info
GET /os/info
GET /addons
GET /jobs/info

Usar as entidades update.* do Home Assistant para atualizações que não são
gerenciadas diretamente pelo Supervisor.

Classificar as atualizações em categorias.

Categorias:

CORE
OS
SUPERVISOR
APP
HACS_SOFTWARE
FIRMWARE
UNKNOWN

============================================================
7. POLÍTICA PADRÃO
============================================================

Home Assistant Core:
AUTO

Home Assistant OS:
AUTO

Supervisor:
AUTO NATIVO DO SUPERVISOR

Home Assistant Apps:
AUTO

HACS / software:
AUTO

Firmware físico:
MANUAL

Unknown:
MANUAL

Nunca atualizar automaticamente algo classificado como UNKNOWN.

============================================================
8. SUPERVISOR
============================================================

Não criar um atualizador paralelo para o Supervisor.

Usar o mecanismo nativo de auto-update.

O App deverá verificar se:

supervisor.auto_update = true

Se não estiver habilitado, oferecer opção para habilitar.

Quando configurado para fazê-lo, utilizar a API oficial do Supervisor.

Não usar endpoint de desenvolvimento para atualização manual do Supervisor.

============================================================
9. BACKUP
============================================================

Criar backup apenas quando existir pelo menos uma atualização que realmente
será instalada naquela execução.

Não gerar backup apenas por causa do reboot diário.

O App deve aguardar a confirmação real da conclusão do backup.

Preferir API do Supervisor com background/job_id.

Exemplo conceitual:

POST /backups/new/full
background: true

Depois acompanhar:

GET /jobs/<job_id>

Só iniciar atualizações depois de:

done = true

Se backup falhar:

- abortar atualizações;
- registrar falha;
- notificar usuário.

O reboot diário permanece uma função independente, desde que não exista job
de backup ainda em andamento.

============================================================
10. ORDEM DE ATUALIZAÇÃO
============================================================

Ordem preferencial:

1. Home Assistant Apps
2. software/HACS
3. Home Assistant Core
4. Home Assistant OS
5. reboot diário do host

Supervisor funciona pelo mecanismo nativo.

Firmware não entra automaticamente nessa fila por padrão.

============================================================
11. HOME ASSISTANT APPS
============================================================

Usar endpoint atual e não endpoint depreciado:

POST /store/addons/<addon>/update

Usar:

background: true

Acompanhar job_id até conclusão.

Não usar o endpoint antigo /addons/<addon>/update como implementação principal.

============================================================
12. CORE
============================================================

Atualizar Core usando API oficial.

Após atualização:

- aguardar Home Assistant voltar;
- verificar versão instalada;
- verificar disponibilidade da API;
- registrar resultado.

O restart provocado pelo update do Core NÃO elimina o reboot preventivo
diário das 05:30.

São funções diferentes.

============================================================
13. HOME ASSISTANT OS
============================================================

Executar update do OS.

Não executar reboot imediatamente se for possível esperar a janela de reboot
diário.

Fluxo desejado:

OS update concluído
        ↓
marcar reboot_required
        ↓
aguardar horário do reboot diário
        ↓
POST /host/reboot
        ↓
App reinicia junto com o sistema
        ↓
retomar estado persistido
        ↓
confirmar nova versão do OS

Isso evita dois reboots próximos.

============================================================
14. FIRMWARE
============================================================

Firmware físico NÃO deve ser atualizado automaticamente por padrão.

Detectar device_class firmware quando disponível.

Deve existir configuração:

automatic_firmware_updates: false

No futuro deverá ser possível implementar:

allowlist
denylist

Exemplo:

permitir determinado ESPHome;
bloquear firmware de equipamento crítico.

Não implementar atualização cega de todo update.*.

============================================================
15. AUTOATUALIZAÇÃO DO PRÓPRIO APP
============================================================

O Smart House Update Manager não deve atualizar a si próprio no meio de uma
rotina.

Seu slug deve estar excluído da fila atual.

A atualização do próprio App será tratada separadamente pelo Home Assistant
App Store/Supervisor.

============================================================
16. ESTADO PERSISTENTE
============================================================

Salvar estado em /data.

O estado deve sobreviver:

- restart do App;
- restart do Core;
- reboot do host;
- atualização do OS.

Exemplo de dados:

run_id
started_at
status
current_step
backup_status
backup_job_id
updates_detected
updates_completed
updates_failed
core_target
os_target
os_reboot_required
daily_reboot_pending
daily_reboot_requested_at
last_boot_timestamp
errors

Na inicialização do App:

se existir execução incompleta:
    retomar e validar estado

Nunca começar uma nova rotina sem resolver a anterior.

============================================================
17. DETECÇÃO DE REBOOT CONCLUÍDO
============================================================

Antes do reboot consultar:

GET /host/info

Salvar boot_timestamp.

Após o App iniciar novamente:

consultar GET /host/info

O novo boot_timestamp deverá ser diferente.

Somente então marcar:

daily_reboot = success

Também validar:

- Supervisor responde;
- Home Assistant responde;
- Core está operacional.

============================================================
18. HEALTH CHECK
============================================================

Após updates/reboots verificar no mínimo:

- Supervisor API online;
- Home Assistant API online;
- Core state operacional;
- versão do Core;
- versão do OS;
- jobs presos;
- update ainda marcado como pendente;
- boot_timestamp após reboot.

Não considerar genericamente qualquer ERROR existente no log como falha da
rotina.

A instalação real já possui integrações com warnings e erros independentes.

Comparar apenas condições relacionadas à execução atual.

============================================================
19. FAIL CLOSED
============================================================

Não implementar continue_on_error global.

Em falhas importantes:

BACKUP FAIL
→ cancelar updates.

UPDATE FAIL
→ interromper a sequência quando necessário.

JOB PRESO
→ não iniciar operação conflitante.

OS UPDATE FAIL
→ não assumir sucesso.

REBOOT BLOQUEADO
→ aguardar e tentar novamente.

Nunca marcar execução como concluída sem validação.

============================================================
20. DRY RUN
============================================================

Implementar modo:

dry_run: true

Nesse modo:

- detectar atualizações;
- classificá-las;
- mostrar plano;
- simular ordem;
- NÃO instalar;
- NÃO gerar backup;
- NÃO reiniciar host.

Deve existir botão no painel para executar Dry Run manual.
